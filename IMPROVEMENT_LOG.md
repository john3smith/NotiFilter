## Cycle 2 - range-based bounded history retention - 2026-10-29

- Problem/cause: each confirmed removal built a 1000-ID NOT IN list and compared the outer history table against it, even though history IDs already form an indexed ordering. Selected as a small, reproducible persistence hot-path improvement; no speculative service reconnection changes.
- Change: delete IDs below the 1000th newest ID using the INTEGER PRIMARY KEY range. Below 1000 rows, a NULL boundary deletes nothing. Insert and prune remain one transaction; encryption, secure deletion and the schema are unchanged. Version 1.0.15 (16).
- Restore point: 6f55a097622f1ce75f5d7b2f26edbe968b8bc5d8, with scoped original files and SHA-256 manifest backed up locally before editing. No automatic reset or user-data restoration.
- Validation: 20 unit tests passed; release/test APK builds passed; lint zero errors/eight warnings. On the regular emulator, nine synthetic retention cases passed (six boundaries, gapped IDs, rollback, idempotence), plus benchmark retained-row counts, eight sorting checks and catalog/edit/picker regressions. Query plan confirms an outer INTEGER PRIMARY KEY range search.
- Measurement: on-disk Android SQLite insert/prune transaction median 48,857.291 us before and 46,364.461 us after (about 5.1% lower), seven samples of 200 transactions after warmup, alternating order and secure deletion ON. Includes emulator disk synchronization; excludes encryption/icons/callbacks. This observation does not establish the same improvement on physical devices or across workloads.
- Verification recovery: test helper PRAGMA changed from execSQL to rawQuery after Android rejected the former. Initial 120-second host timeout expired while the device test continued; waited for it to finish without overlapping/restarting it, then used a 600-second host limit and durable synthetic result file. The final test passed. These were verification-harness failures, not confirmed production failures.
- Runtime: signed API 26-36 release verified; emulator install -r preserved UID and first-install time, version 1.0.15 launched, and pulled installed bytes equal the signed APK. No physical device or real history used as a fixture.
- Self-evaluation/remaining: retention is equivalent under boundaries, gaps and rollback with a cheaper indexed outer delete. Disk latency dominates the measured transaction; full notification latency and battery remain unmeasured. Existing lint warnings remain. Next investigate removal-confirmation bookkeeping, reconnect and asynchronous history-load behavior.
- Delivery: matching protected-branch PR and versioned GitHub Release; source/asset/runtime receipts retained with this cycle. Subsequent cycles remain coordinator-owned.

## Cycle 3 - ordered expiry for pending removal confirmations - 2026-10-29

- Problem/cause: each cancellation request scanned every pending confirmation and read the elapsed clock for each entry, even if no entry had expired. The map is bounded at 1000, but repeated burst requests repeated this work on the service/UI thread. Chosen over speculative reconnection or lifecycle changes because the workload and equivalence can be tested directly.
- Change: extract a main-thread-only ordered pending collection; expire only the oldest prefix, refresh an existing key at the tail, preserve capacity and strictly-greater-than-30s boundary. Capture one monotonic timestamp per request and defer content extraction until admission succeeds. Cancellation failure, reason/age confirmation and disconnect cleanup remain unchanged. Version 1.0.16 (17).
- Restore point: 7087ba50613bf2c0e0e52d4200701568077a082a; original scoped files and SHA-256 manifest saved before edits. Restore only after checking intervening changes; no automatic reset or user-data changes.

Release/test builds passed; lint zero errors/eight warnings. Existing isolated-emulator catalog/edit/picker and eight sorting checks passed. Production install -r preserved UID and first-install time; 1.0.16 launched and installed APK bytes match the signed artifact.
- Measured work: 1000 valid entries at capacity require 1000 timestamp inspections before versus 1 after. Full expiry still requires 1000 inspections. No elapsed-time, memory, battery or end-to-end throughput improvement is claimed.

- Change: supply the current request predicate to HistoryStore; check it before DB access, at each row and main-thread callback delivery. Existing activity request generation is volatile for worker visibility. Current failure behavior and cursor cleanup remain; writes and clear are never cancelled. Version 1.0.17 (18).
- Restore point: 035134583c3e28e8b2b0e9c2cd432e75b1fc0dd3; scoped original files and SHA-256 manifest saved locally before changes. No automatic reset or user-data restore.
- Android evidence: four isolated store checks passed. Of 100 reads queued behind a blocked worker, 99 stale requests skipped DB access and one current result arrived. - Self-evaluation: obsolete expensive reads are avoided without cancelling writes or weakening encryption. Existing layout, permissions, schema, retention and dependencies unchanged. Full physical-device/lifecycle stress remains untested.
- Remaining/next: listener removal-reason attribution, reconnect and broader lifecycle stress remain separate investigation targets. Do not count rechecking this cancellation path as another improvement.
